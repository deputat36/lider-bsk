# Проверка retry-idempotency всех публичных форм

Дата: 2026-07-10.

Связано: #200, #201, #210.

Контур:

`посадочная страница → assets/public-lead-form.js → leader-public-lead v9 → request_id → CRM`.

Supabase production в рамках этого изменения не менялся.

## Что изменено

- pending `request_id` хранится внутри общего `assets/public-lead-form.js`;
- одинаковая заявка после сетевого сбоя повторно использует тот же `request_id`;
- pending state живёт только в `sessionStorage` и не более 30 минут;
- в storage сохраняется FNV-1a fingerprint, а не исходный телефон или текст заявки;
- номера с префиксами `+7` и `8` сравниваются по последним 10 цифрам;
- pending state очищается только после HTTP success и подтверждённого `data.ok === true`;
- `assets/public-lead-reference-v1.js` использует тот же fingerprint и остаётся совместимым с `request.html`.

## Страницы для ручной проверки

Проверить минимум:

1. `request.html` — общий модуль вместе с reference helper;
2. `index.html` — форма на главной;
3. `bannery-borisoglebsk.html` — услуга наружной рекламы;
4. `vizitki-borisoglebsk.html` — полиграфия;
5. `reklama-dlya-kafe-borisoglebsk.html` — бизнес-сценарий.

## Сценарий 1. Повтор после сетевого сбоя

1. Открыть DevTools → Network.
2. Заполнить форму валидным телефоном и задачей.
3. Временно включить Offline непосредственно перед отправкой либо заблокировать запрос к `leader-public-lead`.
4. Нажать «Отправить заявку».
5. Убедиться, что отображается ошибка отправки.
6. Вернуть сеть, не менять данные и отправить повторно.
7. В Network сравнить `request_id` двух попыток.

Ожидается: обе попытки используют один `request_id`.

## Сценарий 2. Изменённая заявка

После неуспешной попытки изменить текст задачи или услугу и отправить снова.

Ожидается: формируется новый `request_id`.

## Сценарий 3. Формат телефона

Первую попытку отправить с телефоном `+7 900 123-45-67`, повторить после сбоя как `8 900 123 45 67`, не меняя остальные данные.

Ожидается: используется тот же `request_id`.

## Сценарий 4. Подтверждённый успех

После ответа `{ ok: true }` проверить sessionStorage.

Ожидается: ключ `leader_public_lead_pending_v1` удалён, форма показывает номер обращения, duplicate-response показывает тот же номер.

## Сценарий 5. Ответ без ok=true

С помощью DevTools Local Overrides или тестового mock вернуть HTTP 200 без `ok: true`.

Ожидается: форма не считает запрос подтверждённым, показывает ошибку, pending `request_id` сохраняется для повторной попытки.

## Сценарий 6. Приватность storage

После неуспешной попытки открыть Session Storage и изучить `leader_public_lead_pending_v1`.

Ожидается:

- есть `request_id`, `fingerprint`, `created_at`;
- fingerprint начинается с `fnv1a-`;
- исходного телефона и текста заявки нет.

## Сценарий 7. Истечение pending state

Подменить `created_at` на значение старше 30 минут и повторить ту же заявку.

Ожидается: старый номер не используется, создаётся новый `request_id`.

## Проверка CRM

После успешной отправки:

1. скопировать номер обращения;
2. открыть CRM → «Аудит заявок»;
3. найти `request_id`;
4. убедиться, что новая заявка имеет полную цепочку;
5. повтор с тем же `request_id` не должен создавать второй lead.

## Автоматический контракт

`node tools/test_public_lead_shared_retry.mjs` проверяет:

- одинаковый payload повторно использует номер;
- изменение payload создаёт новый номер;
- `+7` и `8` нормализуются одинаково;
- raw phone/message не сохраняются;
- expired pending state не используется;
- fingerprint общего модуля и helper совпадает.
