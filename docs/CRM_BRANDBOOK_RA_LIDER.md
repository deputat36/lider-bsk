# Брендбук CRM РА «Лидер»

Версия: 1.0  
Статус: нормативная спецификация рабочего интерфейса CRM.  
Родительский документ: `docs/BRAND_SYSTEM_RA_LIDER.md`.  
Область применения: CRM v4, авторизация, рабочие списки, карточки клиентов и заказов, обращения, потребности, расчёты, предложения, производство, финансы, сотрудники, настройки, служебные уведомления и будущие внутренние модули.

## 1. Роль CRM

CRM — рабочий инструмент сотрудника, а не рекламная витрина.

Главная цель интерфейса — помогать сотруднику быстро понять ситуацию и выполнить следующий правильный шаг без лишних кликов, поиска и визуального шума.

Приоритеты:

1. скорость работы;
2. понятность состояния заказа/клиента;
3. минимизация ошибок;
4. сохранение контекста;
5. предсказуемость действий;
6. доступность критичной информации;
7. только затем декоративность.

## 2. Отличие CRM от публичного сайта

CRM использует тот же бренд, но более спокойную и утилитарную его версию.

Сайт может быть эмоциональнее и визуально выразительнее. CRM должна быть:

- нейтральнее;
- плотнее по информации;
- спокойнее по motion;
- экономнее по orange;
- более строгой по иерархии;
- практически без рекламных декоративных эффектов.

Общее с сайтом:

- официальный логотип;
- Brand Orange `#FF6A00`;
- graphite/neutral palette;
- Manrope/system typography;
- единая line-icon система;
- focus ring;
- радиусы 8/12/16;
- единая spacing logic.

## 3. Визуальный характер CRM

Целевое ощущение:

> «Спокойный профессиональный рабочий кабинет, где всё на своих местах и понятно, что делать дальше».

Не целевое ощущение:

- рекламный лендинг внутри CRM;
- игровой dashboard;
- cyberpunk;
- neon/glow;
- dashboard с десятками ярких цветов;
- набор несвязанных модалок и таблиц;
- «красиво, но непонятно».

## 4. Источник фирменных значений

Брендовые значения берутся из:

`assets/brand/leader-tokens.css`

и переносимого:

`assets/brand/leader-tokens.json`.

Текущий CRM compatibility layer:

`crm/v4/assets/v4/brand-foundations-v2.css`.

Он считается переходным слоем, а не отдельной независимой палитрой. При дальнейшей миграции `--v4-brand-*` должны либо ссылаться на shared tokens, либо постепенно заменяться общими tokens без изменения бизнес-логики.

## 5. Цветовая система CRM

Основные цвета:

- page/canvas — `#F7F7F8`;
- surface/card — `#FFFFFF`;
- primary text — `#171717`;
- deep text/navigation — `#0D0F12`;
- secondary text — `#667085`;
- border — `#E5E7EB`;
- primary action — `#FF6A00`;
- hover action — `#E85F00`;
- soft accent — `#FFF3E8`.

Orange означает:

- главное действие;
- активный элемент навигации;
- выбранный объект;
- focus;
- фирменный акцент.

Orange не означает:

- успех;
- ошибку;
- предупреждение;
- завершение этапа;
- блокировку.

## 6. Семантические цвета

Семантика важнее бренда.

Success:

- green `#168653` или согласованный зелёный;
- soft green background.

Warning:

- amber/brown `#B56A00`;
- soft warning background.

Error/destructive:

- red `#C9362B`;
- soft red background.

Neutral/information:

- graphite/gray;
- при необходимости отдельный информационный blue только как semantic color, а не второй брендовый цвет.

Цвет всегда дублируется текстом, иконкой или формой. Нельзя кодировать состояние только цветом.

## 7. Градиенты и декоративные эффекты

Целевая CRM не использует рекламные градиенты как системный приём.

Текущие gradient/glow решения в `brand-foundations-v2.css` считаются legacy/transitional и должны уменьшаться в последующих UI PR без риска для функциональности.

Допустимо:

- очень слабый neutral background transition;
- редкий controlled gradient только в auth/empty promotional surface, если он не мешает работе.

Не допустимо как стандарт:

- gradient primary button;
- glowing cards;
- radial orange background на каждом экране;
- декоративный pattern в рабочих таблицах;
- анимация ради бренда.

## 8. Логотип и shell

CRM использует официальный бренд, но логотип не должен занимать рабочее пространство.

В desktop shell:

- полный логотип — в auth/entry screen или крупной shell area;
- компактный знак — допустим в узкой sidebar/header area;
- логотип не повторяется внутри каждого модуля.

Header/sidebar всегда уступает место рабочей информации.

## 9. Типографика CRM

Основная гарнитура:

`Manrope, Arial, Helvetica, sans-serif`.

Целевая шкала:

- Page title — 28–32 px / 800;
- Section title — 20–24 px / 700–800;
- Card title — 17–20 px / 700;
- Body/control — 14–16 px / 400–600;
- Label — 13–14 px / 600;
- Meta/caption — 12–13 px / 500;
- Key number — 24–32 px / 700–800.

CRM не использует огромные marketing H1.

Uppercase допускается только для очень коротких технических labels, если это улучшает сканирование. Не использовать uppercase для названий разделов и кнопок.

## 10. Плотность интерфейса

CRM должна быть компактнее сайта, но не тесной.

Целевые уровни:

- comfortable — основная плотность;
- compact — таблицы/списки с большим объёмом;
- touch-safe — mobile/tablet actions.

Типовые интервалы:

- между label и control — 6–8 px;
- между связанными controls — 8–12 px;
- внутри card — 16–20 px;
- между секциями card — 20–24 px;
- между большими рабочими блоками — 24–32 px.

Не применять публичный marketing spacing 64–96 px внутри рабочей карточки.

## 11. Радиусы

- inputs/small controls — 8 px;
- buttons/tabs/selects — 10–12 px;
- cards/panels — 12–16 px;
- dialog — до 16 px.

Pill применяется только для status/chip/tag/count.

## 12. Основная архитектура рабочего экрана

Типовой desktop экран:

1. global navigation;
2. page context/header;
3. primary action или search/filter row;
4. основной рабочий список/объект;
5. detail/action workspace;
6. secondary meta/history.

Главное действие должно находиться рядом с контекстом, которого оно касается.

Не размещать глобальные действия внутри случайных карточек.

## 13. Навигация

Навигация отражает реальные рабочие сущности, а не техническую структуру кода.

Название пункта должно отвечать на вопрос сотрудника:

- Клиенты;
- Обращения;
- Заказы;
- Расчёты;
- Производство;
- Финансы;
- Сотрудники;
- Настройки.

Не выводить пользователю названия таблиц, backend modules, RPC или internal identifiers.

Активный пункт выделяется одним стабильным способом: orange marker/soft background + typography.

## 14. Dashboard

Dashboard нужен только для принятия решений.

Показывать:

- что требует внимания сегодня;
- просроченные действия;
- заказы на ближайшее время;
- новые обращения;
- проблемные статусы;
- короткие KPI, если они действительно используются.

Не показывать декоративные метрики ради заполнения экрана.

Карточка KPI должна иметь:

- название;
- значение;
- период/контекст;
- optional изменение;
- optional переход к списку.

## 15. Рабочие списки

List view должен позволять быстро:

- найти объект;
- понять его состояние;
- увидеть владельца/ответственного;
- понять следующий шаг;
- открыть detail без потери контекста.

Для списка используются:

- search;
- filters;
- sort;
- compact status;
- meaningful secondary text;
- pagination/virtualization при необходимости.

Не превращать каждую строку в большую рекламную карточку.

## 16. Таблицы

Таблица предпочтительна, когда сотрудник сравнивает множество однотипных объектов.

Правила:

- sticky header при длинной таблице;
- ключевой идентификатор/название слева;
- numbers aligned consistently;
- monetary values выровнены и форматированы одинаково;
- status компактный;
- row actions не занимают половину строки;
- horizontal scroll допускается только для действительно широких данных;
- critical column не прячется первой на mobile.

Zebra stripes не обязательны. Предпочтительнее спокойный border/hover.

## 17. Карточка клиента

Первый экран клиента отвечает:

- кто это;
- как связаться;
- какие есть активные обращения/заказы;
- что нужно сделать сейчас;
- история последних действий.

Контакты и primary actions видны без прокрутки на desktop.

История не должна визуально конкурировать с активными задачами.

## 18. Карточка заказа

Карточка заказа — центральный рабочий интерфейс.

Рекомендуемая иерархия:

1. номер/название заказа;
2. клиент;
3. статус и срок;
4. следующий шаг;
5. потребности;
6. расчёт;
7. дизайн/макеты;
8. производство/подрядчик;
9. оплата/финансы;
10. документы;
11. история.

Сотрудник не должен открывать несколько несвязанных окон, чтобы понять заказ целиком.

## 19. Потребности

Потребность — понятное описание того, что клиенту требуется, а не дополнительный бюрократический слой.

Каждая потребность должна иметь минимум:

- тип/название;
- параметры;
- количество;
- optional комментарий;
- связь с расчётом/позицией при необходимости;
- состояние.

Не требовать заполнения полей, которые не нужны конкретному типу работы.

## 20. Расчёт стоимости

Расчёт должен восприниматься как единое рабочее пространство, а не набор «быстрый/сложный» в разных местах.

Обязательные слои:

- позиции;
- количество/единица;
- себестоимость, если роль имеет право видеть;
- наценка/маржа в понятной форме;
- цена клиенту;
- скидка;
- подрядчик/quote, если нужен;
- дополнительные расходы;
- итог;
- прибыльность/контроль только для разрешённых ролей;
- версия/сохранение;
- формирование предложения клиенту.

Финансовые значения должны иметь единую визуальную структуру, а критические изменения — подтверждение.

## 21. Формы

Форма группируется по смыслу, а не по структуре базы.

Правила:

- label всегда виден;
- placeholder не заменяет label;
- required обозначается единообразно;
- help text короткий;
- ошибки появляются рядом с полем;
- сохранять введённые данные после recoverable error;
- autofocus только там, где он действительно ускоряет работу;
- Enter не должен случайно запускать destructive action.

Длинные формы разбиваются на логические sections, а не на декоративные cards ради cards.

## 22. Кнопки и действия

Иерархия:

- Primary — orange;
- Secondary — graphite/neutral;
- Tertiary/ghost — low emphasis;
- Destructive — red;
- Icon action — только с понятной иконкой и accessible name.

На одном рабочем блоке один primary action.

Примеры primary:

- Сохранить;
- Создать заказ;
- Рассчитать;
- Отправить предложение;
- Передать в производство.

Примеры secondary:

- Добавить позицию;
- Изменить;
- Дублировать;
- Скачать;
- Открыть историю.

Destructive action никогда не окрашивается orange.

## 23. Tabs, filters и chips

Tabs используются для устойчивых представлений одного объекта.

Filter chips используются только если реально ускоряют выбор.

Status chips:

- компактные;
- семантические;
- не становятся главным визуальным элементом карточки.

Не делать каждую навигацию pill-tab bar.

## 24. Статусы

Статус должен отвечать на вопрос «что сейчас происходит».

Правила:

- короткое название;
- стабильный цвет;
- optional icon;
- при необходимости пояснение следующего действия;
- одинаковый статус имеет одинаковый вид во всех модулях.

Не создавать несколько названий для одного бизнес-состояния из-за разных экранов.

## 25. Empty state

Empty state сообщает:

1. что здесь должно быть;
2. почему сейчас пусто, если известно;
3. что можно сделать.

Хорошо:

> Расчётов пока нет. Создайте первый расчёт для этого заказа.

Плохо:

> Ничего не найдено :(

Иллюстрация optional и не должна занимать основную часть рабочего экрана.

## 26. Loading state

Использовать:

- skeleton для повторяемого контента;
- inline spinner для локального действия;
- disabled + progress для submit;
- явный статус для долгой операции.

Не блокировать весь интерфейс, если загружается только один модуль.

Не показывать технические детали загрузки пользователю.

## 27. Error state

Ошибка должна объяснять сотруднику следующий шаг.

Пользовательский текст:

- что не получилось;
- сохранены ли данные;
- можно ли повторить;
- куда обратиться, если ошибка повторяется.

Internal error ID допускается вторичным copyable field для поддержки, но не заменяет понятное сообщение.

Не показывать stack trace, SQL, Supabase internals или raw exception в обычном UI.

## 28. Success feedback

Успех подтверждается кратко и без модального окна, если дополнительное решение не требуется.

Предпочтительно:

- inline state;
- toast;
- change of status;
- updated content.

Не показывать celebratory animation за каждое сохранение.

## 29. Toasts

Toast используется для короткого результата действия.

Правила:

- не более 1–3 строк;
- понятный status;
- auto-dismiss только если сообщение не критично;
- ошибка остаётся достаточно долго;
- action «Повторить» допускается, если операция безопасно повторяема.

Toast не заменяет field validation.

## 30. Modal / dialog

Modal используется только когда действие нельзя разумно выполнить inline.

Подходит для:

- подтверждения destructive operation;
- короткого create/edit;
- выбора сущности;
- просмотра небольшого secondary content.

Не подходит для:

- полноценной карточки заказа;
- длинного расчёта;
- многоэтапного рабочего процесса.

Dialog должен иметь focus trap, Escape, явный title и безопасный порядок кнопок.

## 31. Destructive actions

Удаление, отмена, необратимая смена статуса требуют повышенной осторожности.

Правила:

- red destructive button;
- отделение от primary action;
- confirm с названием объекта;
- при серьёзном риске — дополнительное подтверждение;
- после выполнения — понятный результат;
- использовать archive/restore вместо delete, если бизнес-процесс допускает.

## 32. Финансы

Финансовые данные требуют визуальной дисциплины.

- ₽ форматируется одинаково;
- decimals показываются только если нужны;
- себестоимость и цена клиенту визуально различимы;
- скидка не маскирует итог;
- отрицательная прибыльность — semantic warning/error, не orange;
- скрытые по роли данные не должны оставлять пустые подозрительные колонки.

## 33. Permissions и роли

Визуальный интерфейс должен соответствовать разрешениям.

Если действие запрещено:

- лучше не показывать его вообще, если сотруднику оно не нужно;
- disabled допустим, если важно показать существование функции и причину недоступности;
- tooltip/description может объяснить требуемую роль.

Нельзя полагаться только на скрытие UI как на безопасность backend.

## 34. История и аудит

History/audit presentation вторична к рабочему действию, но должна быть доступна.

Запись истории показывает:

- что произошло;
- когда;
- кто;
- ключевое изменение.

Не выводить сырой JSON как основной формат истории.

## 35. Иконки

Использовать одну line-icon систему, совместимую по стилю с `assets/brand/leader-icons.svg`.

Иконка:

- не заменяет текст в критическом действии;
- имеет tooltip/accessible name в icon-only control;
- не смешивается с emoji;
- имеет одинаковую optical size в toolbar.

## 36. Search

Search — глобальный рабочий инструмент.

Поиск должен:

- принимать естественные ключи: имя, телефон, номер заказа и т. п.;
- явно показывать, где ищет;
- сохранять фильтры, если сотрудник возвращается к списку;
- позволять очистить запрос одним действием;
- не запускать тяжёлый запрос на каждый символ без debounce/appropriate strategy.

## 37. Responsive CRM

CRM в первую очередь desktop/tablet, но основные действия должны быть доступны на mobile.

На mobile:

- рабочий список → detail stack;
- secondary panels collapse;
- primary action остаётся доступным;
- touch target минимум 44 px;
- таблица превращается в адаптивный list там, где horizontal scroll разрушает работу;
- сложный расчёт может использовать horizontal scroll только внутри контролируемой области.

Не пытаться буквально сжать desktop layout до 360 px.

## 38. Accessibility

Обязательные требования:

- keyboard navigation;
- visible focus;
- semantic labels;
- WCAG AA contrast;
- dialogs with accessible title;
- table headers associated with data;
- error text linked to field;
- icon-only buttons have accessible name;
- status not encoded only by color;
- reduced motion respected.

## 39. Keyboard productivity

Для часто повторяемых действий допустимы shortcuts, если:

- они не конфликтуют с браузером;
- доступны в подсказке;
- не обязательны для выполнения операции;
- destructive shortcut требует безопасного подтверждения.

Enter/Space behaviour должно соответствовать стандартным controls.

## 40. Tone of Voice внутри CRM

CRM говорит коротко и операционно.

Хорошо:

- «Сохранить расчёт»;
- «Телефон клиента не указан»;
- «Не удалось сохранить. Данные остались в форме. Повторите попытку.»;
- «Передать в производство».

Плохо:

- «Что-то пошло не так» без пояснения;
- «Success!»;
- «Fatal error»;
- «RPC failed»;
- рекламные фразы внутри рабочего процесса.

## 41. Формат данных

Дата:

- в основном UI — `15.09.2026` или `15 сентября` в зависимости от контекста;
- время — `14:35`;
- точный timestamp — в audit/detail при необходимости.

Деньги:

- `12 500 ₽`;
- `12 500,50 ₽` только когда копейки имеют смысл.

Телефон:

- читаемый формат;
- copy/call action рядом при необходимости.

IDs:

- показывать только те идентификаторы, которые реально нужны сотруднику.

## 42. Charts и аналитика

Chart появляется только если помогает увидеть изменение, сравнение или проблему.

Правила:

- neutral grid;
- orange — главная серия/акцент;
- semantic colors — статусы;
- не использовать rainbow palette;
- не использовать 3D charts;
- всегда показывать units/period;
- таблица или число должны быть доступны, если график не читается.

## 43. Brand motif в CRM

Диагональная восходящая геометрия логотипа почти не используется внутри рабочего пространства.

Допустимые места:

- auth screen;
- empty onboarding screen;
- very subtle shell accent.

Не использовать:

- в каждой карточке;
- в таблицах;
- вокруг inputs;
- как background для расчётов/финансов.

## 44. Текущий `brand-foundations-v2.css`

Файл сохраняется как compatibility layer, но дальнейшие PR должны постепенно привести его к целевой системе.

В частности, целевое направление:

- primary button: gradient → flat `#FF6A00`;
- hero/shell: уменьшить рекламные gradients;
- orange soft panels использовать только для действительно активного/фирменного акцента;
- снизить тяжёлые shadows;
- заменить pill kicker там, где это не status/tag;
- связать значения с shared `leader-tokens.css`;
- сохранить semantic green/yellow/red statuses.

Каждое изменение делается отдельно от бизнес-логики.

## 45. Правило безопасной UI-миграции

Запрещено одновременно в одном PR:

- менять business logic;
- переделывать DOM contract;
- менять permissions;
- менять backend schema;
- и полностью менять UI одного крупного модуля.

Предпочтительный порядок:

1. token alignment;
2. shell/navigation;
3. buttons/forms/statuses;
4. lists/tables;
5. order card;
6. calculation workspace;
7. client/lead pages;
8. production/finance;
9. settings/admin;
10. удаление legacy decorative CSS.

После каждого шага — regression tests.

## 46. Definition of Done для CRM-экрана

Экран соответствует брендбуку, если:

- использует общую graphite/orange/neutral систему;
- orange не заменяет semantic status colors;
- primary action один и понятен;
- destructive action red и отделён;
- форма имеет labels/errors/focus;
- list/table легко сканируется;
- status одинаков с другими модулями;
- loading/empty/error/success states предусмотрены;
- нет emoji и случайной iconography;
- нет рекламного gradient/glow без функции;
- mobile/tablet сценарий не разрушен;
- keyboard/focus работают;
- разрешения и скрытие данных не изменены presentation-layer правками;
- нет raw backend/infrastructure текста в обычном UI;
- CI и module regression checks проходят.

## 47. Эталон восприятия

После полной миграции сотрудник должен воспринимать CRM так:

> «Я быстро вижу, что происходит с клиентом или заказом, понимаю следующий шаг и могу выполнить его без поиска по системе».

Если новый дизайн делает CRM эффектнее, но замедляет сотрудника, он не соответствует брендбуку.
