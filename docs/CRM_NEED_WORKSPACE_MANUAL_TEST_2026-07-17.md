# Проверка рабочего блока потребности

Дата: 17 июля 2026 года.

## Результат для сотрудника

Сохранённая потребность больше не оставляет под собой постоянную форму добавления. Карточка открывается в режиме просмотра и предлагает одно основное действие `Перейти к расчёту`.

Дополнительные действия:

- `Изменить` обновляет ту же потребность;
- `Добавить ещё одну позицию` создаёт отдельную новую потребность;
- `Создать копию` является явным намерением сохранить похожую позицию;
- `Архивировать` скрывает потребность из активной работы без окончательного удаления.

## Desktop и mobile

1. Открыть заявку без активных потребностей.
2. Убедиться, что доступно действие `Добавить потребность`.
3. Заполнить короткий бриф и сохранить.
4. Убедиться, что форма закрылась, появилась карточка, а главное действие — `Перейти к расчёту`.
5. Нажать `Изменить`, проверить заполнение всех сохранённых полей и сохранить изменения.
6. Убедиться, что количество карточек не увеличилось.
7. Нажать `Добавить ещё одну позицию`, сохранить отличающуюся потребность и проверить появление второй карточки.
8. Нажать `Создать копию`, сохранить без изменений и проверить, что копия создаётся только после явного действия.
9. Повторить на ширине 390 px: карточка и действия не должны создавать горизонтальную прокрутку.

## Защита от дублей

1. Открыть обычное добавление, полностью повторить активную потребность и сохранить.
2. Ожидается сообщение `Дубль потребности не создан`; количество карточек не меняется.
3. Быстро дважды нажать кнопку сохранения.
4. Ожидается один INSERT: второе событие блокируется `saveBusy`.
5. Смоделировать потерю ответа после успешного INSERT и повторить сохранение с тем же открытым черновиком.
6. Ожидается повторная проверка стабильного UUID; вторая строка не создаётся, интерфейс восстанавливает существующую запись.

## Network

- Открытие, закрытие, копирование полей и проверка локального дубля не выполняют запросов.
- Создание выполняет один INSERT с UUID текущего черновика.
- Редактирование выполняет UPDATE только по `id` и `lead_id` текущей заявки.
- При ошибке INSERT разрешён только read-back по тому же `id` и `lead_id`.
- Модуль не выполняет DELETE.

## Роли

- `owner`, `admin` и `manager` с активным профилем видят карточки и действия записи.
- Роль без `needs.read` не запускает SELECT и получает понятное сообщение об отсутствии доступа.
- Роль без `needs.write` не видит добавление, изменение, копирование и архивирование.
- Переход к расчёту требует отдельного permission `calculations.write`.
- Эти проверки fail closed в UI; полное server-side enforcement остаётся отдельным staging/production этапом.

## Границы проверки

Production schema, RLS, grants, Edge Functions, Auth, Storage и исторические строки не меняются. Полная межустройственная идемпотентность требует будущего server command; текущий этап предотвращает двойное нажатие, одинаковый активный дубль и повтор текущего браузерного черновика.
