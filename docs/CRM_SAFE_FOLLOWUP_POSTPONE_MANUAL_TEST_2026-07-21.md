# Ручная проверка безопасного переноса следующего контакта

Дата: 21 июля 2026 года.

Связано с issue #400 и #205.

## Цель

Проверить, что быстрый перенос следующего контакта не затирает реальный этап заявки и помогает быстро найти просроченные контакты.

## Подготовка

Использовать согласованную учебную заявку или синтетические данные staging. Не переносить реальные контакты только ради теста.

## Очередь контактов

1. Открыть раздел `Заявки`.
2. Найти блок `Кому связаться сегодня`.
3. Убедиться, что заявки с датой в прошлом помечены `Просрочено`.
4. Убедиться, что сегодняшняя будущая дата помечена `Сегодня`.
5. Проверить текст: перенос даты не меняет текущий этап заявки.

## Сохранение этапа

Проверить минимум три учебных сценария.

### КП отправлено

1. Исходный статус — `КП отправлено`.
2. Нажать `+1 час` или `Завтра 10:00`.
3. Проверить новую дату контакта.
4. Статус должен остаться `КП отправлено`.
5. В истории должна появиться запись `Следующий контакт`.

### Нужно пересчитать

1. Исходный статус — `Нужно пересчитать`.
2. Перенести дату.
3. Статус должен остаться `Нужно пересчитать`.
4. Помощник не должен возвращать заявку в `Ждём ответ`.

### Новая заявка

1. Исходный статус — `Новая`.
2. Назначить повторный контакт.
3. Статус может перейти в `Ждём ответ` по существующему правилу первого контакта.
4. История должна отражать и дату, и переход этапа.

## Терминальная заявка

1. Использовать учебную заявку со статусом `Отказ`, `Спам`, `Не отвечает`, `Дорого`, `Передумал` или `Создан заказ`.
2. Она не должна попадать в рабочую очередь переноса.
3. Pure model не должен формировать для неё patch.

## Частичный результат истории

1. Смоделировать недоступность истории после успешного обновления даты.
2. CRM должна сообщить: дата сохранена, история требует проверки.
3. После обновления страницы новая дата сохраняется.
4. Статус остаётся исходным.
5. Недостающую запись можно добавить вручную в истории заявки.

## Двойной клик

1. Быстро дважды нажать кнопку переноса.
2. Пока первый запрос выполняется, второй не должен запускаться.
3. Дата не должна перескочить два раза.
4. В истории не должно появиться две записи одного пользовательского действия.

## Фильтр и счётчик

1. В статистике списка найти счётчик `Просрочен контакт`.
2. Он должен считать активные заявки, где `next_contact_at` меньше текущего времени.
3. В фильтре статуса выбрать `Просрочен контакт`.
4. Должны остаться только активные просроченные заявки.
5. Заявки без даты не должны считаться просроченными.
6. Терминальные заявки не должны попадать в фильтр.
7. На карточках списка должна отображаться метка `Контакт просрочен`.

## Mobile

Проверить на ширине 360–430 px:

1. Блок контактов не создаёт горизонтальную прокрутку.
2. Кнопки `+1 час` и `Завтра 10:00` доступны для нажатия.
3. Новый счётчик корректно переносится.
4. Метка `Контакт просрочен` не перекрывает имя или статус заявки.

## Production boundary

В рамках изменения запрещены:

- перенос реальных дат контакта для тестирования;
- массовое исправление восьми просроченных заявок;
- DDL или DML в production Supabase;
- изменение Auth, RLS, grants, Storage, secrets или Edge Functions production;
- создание нового прямого browser-write файла;
- автоматическое закрытие, отказ или изменение коммерческого этапа заявки.

Production используется только для агрегатной read-only диагностики. Staging допускает синтетические записи без персональных данных с обязательной очисткой.
