# Загрузка профиля CRM — 15.10.2026

## Наблюдение

На телефоне после входа показано «Профиль CRM не подтверждён». Точечная
проверка аккаунта подтвердила активный owner, совпадение Auth/profile ID и
подтверждённый email. RLS SELECT в read-only транзакции с ролью authenticated
и соответствующим sub возвращает профиль. Роли, grants и policies не менялись.

В ограниченном окне около 07:15 МСК edge logs показывают успешные запросы
профиля: HTTP 200, одна строка. Серверное время ответа 82–1344 мс. Это не
измеряет доставку/обработку ответа на телефоне и не доказывает конкретную
причину browser exception. PostgREST также имеет timeout notices, но их связь
с этим запросом не установлена. Секреты, токены, IP, email и UUID реального
аккаунта не копируются в репозиторий или CI artifacts.

## Подтверждённая недоработка

Старый клиент ожидал профиль 5000 мс. Error с текстом «Профиль доступа не
загрузился вовремя» не распознаётся общим isNetworkError: строка не содержит
failed to fetch/network/timeout/ожид. Поэтому задержка ошибочно выглядела как
неподтверждённый профиль. Кнопки повтора без выхода из аккаунта не было.
Это воспроизводимый дефект клиента; точная browser exception на телефоне
пользователя не получена, сетевой сбой остаётся вероятной причиной инцидента.

## Изменение

- Бюджет чтения профиля 15000 мс. Deadline имеет собственный profile_timeout,
  отменяет этот GET через AbortController и предлагает «Повторить проверку».
- Retry перечитывает текущую session и профиль, не запрашивает пароль,
  не выходит из аккаунта и не вызывает ensure_profile при ошибке чтения.
  Двойной клик не запускает второй retry.
- Новый запуск/выход отменяет прежнее чтение. Generation и текущий user ID
  исключают применение поздних session/profile ответов. Выход сразу скрывает
  данные и остаётся scope:local; storage других приложений не затрагивается.
- Для готовности нужны профиль того же user_id, непустая роль и is_active=true.
  Отказ, неактивный или неверный профиль не достигает crmReady. ensure_profile
  для действительно отсутствующего профиля сохраняет прежний pending path.
- HTML/importmap обновляют auth/config согласованно. Исторический auth URL
  разрешается в тот же новый модуль, 11 eager entrypoints сохраняются.

Production Supabase использован только для SELECT/log reads и транзакционного
read-only RLS proof. Auth/профили/роли/RLS/grants/Edge/Storage/рабочие записи не
изменялись. Frontend не подменяет профиль кэшем или фиктивной активной ролью.

## Проверка

Сохранены пять прежних profile-first сценариев. Новый Chromium regression
использует фактические auth/api/state/ui, ограниченный mock Supabase и внешнюю
HTTP block: 360/390/1440; slow success, deadline и retry без пароля, двойной клик,
поздний ответ, logout, смена аккаунта, inactive/403, чужой профиль, пустая роль.
Тестовый clock масштабирует только profileMs в 25 раз с сохранением реального
соотношения 5000/15000; SDK mock не подменяет timeout/classifier/state/UI.
Screenshots и report содержат только синтетические записи. Fixture proof не
объявляется успешным входом на устройстве пользователя. CI/Pages и exact-head
визуальная проверка фиксируются в PR выпуска.
