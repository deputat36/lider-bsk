# Проверка перехода из расчёта в КП

Дата: 17 июля 2026 года.

## Результат для сотрудника

Сохранённый расчёт без КП показывает главное действие `Сформировать КП`. Кнопка переносит сотрудника к форме КП и подставляет выбранную версию. Если свободный расчёт только один, он выбирается автоматически.

Расчёты, уже связанные с КП или заказом, а также расчёты без положительной суммы клиенту не предлагаются для повторного КП.

## Desktop

1. Открыть заявку с одним сохранённым расчётом без КП.
2. Убедиться, что в карточке расчёта есть главное действие `Сформировать КП`.
3. Нажать кнопку и проверить прокрутку к блоку КП.
4. Убедиться, что нужный расчёт уже выбран, а курсор находится в названии КП.
5. Проверить название, срок и дополнительные условия; фактическое сохранение выполнять только на согласованном тестовом контуре.
6. Открыть заявку с несколькими свободными расчётами: без перехода из карточки форма требует выбрать версию, а переход из карточки подставляет именно её.

## Mobile

1. Повторить сценарий на ширине 390 px.
2. Главное действие расчёта должно оставаться заметным и не создавать горизонтальную прокрутку.
3. Заголовок формы и пояснение должны складываться в одну колонку.

## Защита от повторного КП

1. Для расчёта с `commercial_offer_id` кнопка `Сформировать КП` отсутствует.
2. Этот расчёт отсутствует в списке формы.
3. Для расчёта с `order_id` повторное КП также недоступно.
4. Расчёт с `client_total <= 0` не предлагается до исправления суммы.
5. Если КП существует по `calculation_id`, но обратная ссылка расчёта не обновилась после прежней частичной ошибки, повтор также блокируется.
6. Если список существующих КП не загрузился, форма создания fail closed до успешного чтения.

## Роли

- без `calculations.read` карточки расчётов скрываются текущей role matrix;
- без `offers.read` список КП не запрашивается и показывается понятное сообщение;
- без `offers.write` кнопка следующего действия и форма создания КП скрыты;
- клик и фактическое создание повторно проверяют `offers.write` и fail closed.

## Network

- выбор расчёта, прокрутка и подстановка версии не выполняют Fetch/XHR;
- открытие формы не создаёт КП и не меняет расчёт;
- текущий фактический сценарий создания КП остаётся историческим browser-write и не считается атомарным;
- после успешного INSERT новое КП сразу попадает в локальное состояние, поэтому ошибка следующего шага не оставляет кнопку повтора в текущей сессии;
- перевод создания КП на server command является отдельным staging-first этапом.

## Production boundary

В этом этапе не выполняются production/staging DDL или DML, не меняются RLS, grants, Auth, Storage, Edge Functions и реальные строки. Проверка фактического создания КП требует согласованного тестового пользователя и отдельного безопасного контура.
