# Аудит целостности версий расчёта CRM

Дата: 15 июля 2026 года.

Статус: source-only UX и контракт. Supabase не изменялся.

## Причина

Текущий клиентский код присваивает номер новой версии по формуле:

`количество загруженных расчётов + 1`.

Такая формула не гарантирует уникальность и не учитывает пропуски, параллельные сохранения и исторические дубли. Кроме того, прямое редактирование сохранённого расчёта опасно: конкретная версия может уже использоваться коммерческим предложением или заказом.

## Read-only проверка production

Проект: `ofewxuqfjhamgerwzull`.

На момент проверки:

- сохранённых расчётов: 11;
- сохранённых строк: 30;
- черновиков: 2;
- расчётов с другим статусом: 9;
- расчётов, связанных с КП: 8;
- расчётов, связанных с заказом: 5;
- обнаружена одна пара повторяющихся номеров: у одной заявки две записи с номером версии 1;
- у этой же заявки имеются три расчёта с диапазоном версий от 1 до 3.

Данные не исправлялись и не перенумеровывались.

## Проверка доступа

Для таблиц:

- `public.leader_lead_calculations`;
- `public.leader_lead_calculation_items`

действуют политики `ALL` для роли `authenticated` через общий предикат `leader_private.leader_has_access()`.

Это означает, что новый сценарий версионирования нельзя безопасно реализовывать дополнительными прямыми browser INSERT/UPDATE/DELETE. Для него нужен отдельный серверный action с проверкой активного профиля, роли, идемпотентности и атомарности.

## Staging

Проект: `otulfnouybahfnsycxqn`.

Staging активен и содержит существующий design-task harness, включая:

- `leader_private.leader_command_receipts`;
- защищённые таблицы задач дизайна;
- Edge Function `leader-crm-design` с `verify_jwt=true`.

Таблицы расчётов в staging пока отсутствуют. В рамках данного этапа миграции, таблицы, данные и Edge Functions staging не изменялись.

## Принятое решение

1. Сохранённый расчёт и его строки рассматриваются как историческая версия.
2. Если версия связана с КП, заказом или уже не является черновиком, интерфейс явно показывает защиту источника.
3. Любые изменения должны создавать отдельную новую версию.
4. Номер новой версии должен вычисляться как `max(version_number) + 1` внутри серверной транзакции и блокировки по заявке.
5. Текущие дубли нельзя автоматически перенумеровывать: необходим отдельный аудит связей и явное разрешение на production remediation.
6. Уникальный индекс `(lead_id, version_number)` допустим только после устранения исторических дублей.
7. Исходная версия, её КП и заказ не должны автоматически перепривязываться к новой версии.

## Изменения интерфейса

Добавлен read-only контроль:

- следующего ожидаемого номера версии;
- повторяющихся номеров;
- последней и предыдущих версий;
- связи с КП;
- связи с заказом;
- статуса, отличного от черновика;
- запрета автоматической перезаписи или перенумерации.

Контроль не создаёт новых Network requests и не меняет данные.

## Следующий серверный этап

Формальный action: `calculation.create_version`.

Контракт находится в:

- `contracts/calculation-create-version-server-contract-v1.json`;
- `docs/CRM_CALCULATION_CREATE_VERSION_SERVER_CONTRACT_2026-07-15.md`.

До применения в staging требуется явное разрешение на DDL/Edge deployment. Production потребует отдельного разрешения после успешной проверки staging.

## Границы

Не изменялись:

- production Supabase;
- staging Supabase;
- RLS, grants и Auth;
- Edge Functions;
- существующие расчёты и их строки;
- связи расчётов с КП и заказами;
- `nav_*`, `parket_*`, `broker_*`.
