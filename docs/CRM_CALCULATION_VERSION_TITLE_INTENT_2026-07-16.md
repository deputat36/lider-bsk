# Заголовок новой версии расчёта

Дата: 16 июля 2026 года.

## Проблема

Редактор сразу показывал предполагаемый номер новой версии в названии, например:

`Баннер — правки v3`.

Перед production legacy INSERT выполняется fresh preflight. Если за время редактирования другой сотрудник уже создал версию 3, новая запись правильно получает номер 4, но ранее введённый автоматический заголовок мог остаться `v3`.

В staging номер назначается сервером внутри транзакции, поэтому browser также не может заранее гарантировать окончательный номер.

## Title intent

Черновик теперь различает:

- автоматический заголовок;
- пользовательский заголовок.

Автоматический заголовок вычисляется из:

- исходного названия расчёта;
- текущего `draft.nextVersion`.

Пока сотрудник не менял поле вручную, изменение `nextVersion` автоматически обновляет и название.

Пример:

```text
Баннер — правки v3
→ fresh preflight назначил nextVersion=4
→ Баннер — правки v4
```

Если сотрудник ввёл собственное название, например `Согласованный вариант для клиента`, оно сохраняется при любом изменении номера версии.

Очистка пользовательского поля возвращает автоматический режим.

## Production legacy

После fresh preflight редактор присваивает новый `nextVersion` черновику.

Вычисляемый `title` автоматически получает тот же номер. Поэтому поля:

- `version_number`;
- автоматический суффикс `vN`

не расходятся.

Пользовательское название не перезаписывается.

## Staging Edge/RPC

Browser не отправляет автоматический заголовок в Edge payload:

```json
{
  "title": null
}
```

Это позволяет RPC сформировать заголовок после фактического назначения `max(version_number) + 1` внутри транзакции.

Пользовательское название передаётся явно и сохраняется без изменений.

## Payload boundary

Определение title intent не добавляет:

- browser writes;
- прямой RPC;
- service-role данные;
- actor fields;
- totals;
- version number;
- КП/order links.

## Проверки

Unit tests подтверждают:

- автоматический `v3` меняется на `v4` при обновлении `nextVersion`;
- пользовательское название остаётся после смены версии;
- очистка названия возвращает автоматический режим;
- staging transport отправляет `title=null` для автоматического названия;
- staging transport передаёт пользовательское название;
- server-derived и parent fields не попадают в payload.

## Supabase boundary

В рамках этапа:

- production и staging Supabase не меняются;
- migrations не применяются;
- Edge Functions не развёртываются;
- Auth, RLS, grants и policies не меняются;
- существующие расчёты не переименовываются.
