# CRM: staging-проверка ответственности в очереди контактов

Дата: 21 июля 2026 года.

## Контур

- Staging project: `lider-bsk-staging`.
- Production использовался только для read-only агрегатов.
- Production данные, DDL, RLS, grants, Auth, Storage и Edge Functions не изменялись.

## Синтетический сценарий

Создана одна staging-заявка:

- статус `КП отправлено`;
- просроченная дата следующего контакта;
- `assigned_to = NULL`.

Использованы два синтетических UUID сотрудников без создания Auth-пользователей.

## Проверка самоназначения

Первый conditional UPDATE:

```sql
where id = synthetic_lead
  and assigned_to is null
```

Результат:

- одна строка обновлена;
- назначен первый сотрудник;
- статус остался `КП отправлено`.

Второй конкурентный UPDATE другого сотрудника с тем же условием вернул ноль строк.

Подтверждено:

- `first_assignment_succeeded = true`;
- `second_assignment_rows = 0`;
- первый ответственный не перезаписан.

## Проверка переноса чужой заявки

UPDATE даты с условием:

```sql
where id = synthetic_lead
  and assigned_to = second_user
```

вернул ноль строк.

Подтверждено:

- `wrong_owner_postpone_rows = 0`;
- дата не изменилась;
- статус не изменился.

## Проверка переноса текущего ответственного

UPDATE даты с условием:

```sql
where id = synthetic_lead
  and assigned_to = first_user
```

обновил одну строку.

Итог:

- новая дата сохранена;
- `assigned_to` остался первым сотрудником;
- статус остался `КП отправлено`;
- `stage_preserved = true`.

## Очистка

Синтетическая заявка удалена.

Контроль:

- `synthetic_rows = 0`.

## Итог

Staging подтвердил compare-and-set самоназначение и защиту переноса по текущему ответственному. Вторая сессия и чужой сотрудник не могут изменить заявку из устаревшей вкладки.
