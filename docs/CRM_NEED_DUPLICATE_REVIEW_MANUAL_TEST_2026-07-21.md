# CRM: безопасная проверка дублей потребностей

Дата: 21 июля 2026 года.

## Цель

Проверить, что CRM показывает исторические дубли, не скрывает записи и не позволяет архивировать потребность без проверки связанных расчётов, КП и заказов.

## Production boundary

- Production Supabase не изменять во время проверки разработки.
- Не архивировать реальные потребности без отдельного решения владельца.
- Не выполнять массовый backfill, DELETE или UPDATE исторических записей.
- Не создавать вымышленные заявки и потребности в production.

## Read-only baseline

Production-аудит выявил одну заявку с семью историческими записями одного fingerprint:

- 4 записи уже имеют статус `Архив`;
- 3 активные записи имеют статус `Черновик`;
- 2 активные записи являются лишними относительно одной основной;
- активные записи не связаны с расчётами, КП и заказами.

Интерфейс должен показать только активную группу из трёх записей. Архивные записи не должны увеличивать счётчик активных дублей.

## Desktop

1. Открыть карточку заявки, где есть три активные одинаковые потребности.
2. Убедиться, что счётчик показывает:
   - общее число активных потребностей;
   - число вероятных лишних дублей.
3. Убедиться, что над карточками появился сворачиваемый блок `Найдены вероятные дубли`.
4. Раскрыть блок.
5. Проверить, что:
   - отображается одна группа;
   - указано три одинаковые записи;
   - одна запись отмечена `Рекомендуется оставить`;
   - две записи отмечены `Вероятный дубль`;
   - архивные записи не показываются.
6. Нажать запись в блоке проверки — соответствующая карточка должна прокрутиться в центр и кратковременно подсветиться.
7. У основной карточки должна быть зелёная пометка.
8. У более поздних дублей должна быть оранжевая пометка.

## Безопасное архивирование дубля

1. Нажать `Архивировать дубль` у более поздней записи.
2. До появления подтверждения в Network должен выполниться только read-only SELECT к `leader_lead_calculations` с фильтром по `need_id` записей группы.
3. Если связей нет, CRM должна показать явное подтверждение, что архивируется только выбранная запись, а основная останется активной.
4. Нажать `Отмена` — UPDATE не должен выполняться.
5. Повторить и подтвердить только на согласованной тестовой записи staging.
6. После успешного архивирования:
   - меняется статус только выбранной записи на `Архив`;
   - остальные записи сохраняются;
   - группа пересчитывается;
   - история не удаляется физически.

## Блокировка основной записи

1. Нажать `Проверить архивирование` у рекомендуемой основной записи.
2. CRM должна выполнить dependency preflight.
3. Если в группе есть более поздние безопасные дубли, основная запись не архивируется.
4. Должно появиться сообщение: сначала архивируйте более поздний дубль.
5. UPDATE к `leader_lead_needs` не выполняется.

## Связанный расчёт, КП или заказ

На staging подготовить одинаковую группу, где одна запись связана с расчётом.

1. Нажать архивирование связанной записи.
2. CRM должна заблокировать действие.
3. В сообщении должны быть указаны найденные связи: расчёт, КП и/или заказ.
4. Подтверждение архивирования не показывается.
5. UPDATE не выполняется.
6. Запись со связями должна быть выбрана основной моделью, даже если создана позже.

## Повторный клик и ошибки сети

1. Дважды быстро нажать архивирование одного дубля.
2. Должен выполняться один preflight и не более одного UPDATE после подтверждения.
3. При ошибке SELECT архивирование блокируется, данные не меняются.
4. При ошибке UPDATE карточка остаётся активной, показывается понятная ошибка.

## Mobile 360–430 px

1. Блок проверки должен занимать одну колонку.
2. Кнопки записей должны быть полноширинными и не выходить за экран.
3. Карточка потребности и действия должны перестраиваться в одну колонку.
4. Текст причины блокировки должен полностью читаться без горизонтальной прокрутки.

## Ожидаемый результат

Сотрудник видит исторические дубли, понимает, какую запись оставить, и не может случайно архивировать запись, связанную с расчётом, КП или заказом. Production-данные не меняются автоматически.
