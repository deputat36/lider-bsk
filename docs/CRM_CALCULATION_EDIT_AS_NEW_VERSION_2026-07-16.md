# Правки расчёта через новую версию

Дата: 16 июля 2026 года.

## Проблема

В карточке существующей заявки два модуля использовали один DOM-контейнер `calculationsBox`:

- единый конструктор расчёта;
- список сохранённых версий.

Модуль сохранённых версий мог полностью заменить содержимое контейнера после того, как единый конструктор уже был отрисован. В результате сотрудник видел старые расчёты, но не видел форму нового расчёта и не мог внести правки без создания новой заявки.

Это интерфейсная ошибка. Новая заявка для изменения стоимости, количества, материала или состава работ не требуется.

## Исправленный сценарий

В каждой существующей заявке постоянно доступны два действия:

1. `Новый пустой расчёт` — открывает единый конструктор для ещё одного независимого расчёта в этой же заявке.
2. `Изменить / новая версия` — копирует выбранный сохранённый расчёт в отдельный редактируемый черновик.

При создании новой версии:

- копируются все позиции;
- сохраняются категория, тип, единица, количество, себестоимость, цена клиенту, комментарий и структурированные характеристики;
- можно менять название, потребность и комментарий для клиента;
- можно менять количество, себестоимость и цену каждой строки;
- можно удалить строку;
- можно добавить новую ручную позицию;
- суммы, прибыль и маржа пересчитываются сразу;
- старая версия не обновляется и не удаляется;
- существующие КП и заказ продолжают ссылаться на старую версию;
- новая запись получает статус `Черновик`;
- новая запись не наследует `commercial_offer_id` и `order_id`.

## Номер версии

Номер новой версии определяется не по количеству строк, а по правилу:

`max(version_number) + 1`.

Для production legacy path редактор повторно читает номера версий текущей заявки, чтобы не использовать устаревшее значение интерфейса.

Для staging Edge/RPC номер вычисляется сервером внутри транзакции и advisory lock. Browser не передаёт `version_number`.

Исторические дубли не перенумеровываются автоматически.

## Fresh preflight production legacy

До открытия редактора текущий загруженный список проверяется на повторяющиеся номера версий. Если у одной заявки уже есть две одинаковые версии, действие `Изменить / новая версия` блокируется с понятным сообщением.

Непосредственно перед production browser INSERT выполняется fresh read:

`id, version_number, updated_at`.

После него редактор проверяет:

- исходный расчёт всё ещё существует;
- `updated_at` исходного расчёта совпадает со значением на момент открытия редактора;
- у заявки нет повторяющихся номеров версий;
- следующий номер вычислен по свежему списку как `max(version_number) + 1`.

При ошибке preflight INSERT расчёта и позиций не выполняется. Пользователь получает одно из понятных состояний:

- исходный расчёт удалён или недоступен;
- исходный расчёт изменился после открытия;
- найдены повторяющиеся номера версий.

Эта browser-проверка уменьшает риск production legacy path, но не заменяет серверную транзакцию и уникальный индекс.

## Исправление конфликта контейнеров

Добавлен browser compatibility layer:

- сохранённые версии перемещаются в отдельный `savedCalculationsWorkspace`;
- единый конструктор восстанавливается в `calculationsBox`;
- `MutationObserver` повторяет восстановление после обновления списка сохранённых расчётов;
- сохранённый список и конструктор больше не заменяют друг друга;
- старый дублирующий упрощённый список конструктора скрывается визуально;
- подробный список сохранённых версий остаётся основным.

## Маршрут сохранения

Редактор выбирает путь только по exact staging URL из `V4_CONFIG.supabaseUrl`.

### `staging_edge`

Используется только при URL проекта `otulfnouybahfnsycxqn`.

Редактор:

- проверяет canonical permission `calculations.write`;
- сохраняет стабильный idempotency key на время работы с черновиком;
- передаёт source calculation и его `updated_at`;
- вызывает `leader-crm-calculations` через текущую JWT-сессию;
- передаёт только разрешённую проекцию строк;
- после успеха перечитывает список расчётов;
- показывает отдельную подпись «Тестовый staging».

В этом режиме browser INSERT/DELETE не выполняются. Расчёт, позиции и receipt создаются атомарно через Edge/RPC.

### `production_legacy`

Используется для текущего production URL `ofewxuqfjhamgerwzull` и любого URL, который не является exact staging URL.

Сохраняется действующий двухшаговый механизм:

1. выполняется fresh preflight источника и версий;
2. создаётся расчёт;
3. создаются его позиции;
4. при ошибке позиций выполняется compensating delete пустого расчёта.

Этот fallback не может включиться в staging-ветке. Production server action не включается данным этапом.

## Idempotency и payload

Для staging создаётся ключ формата:

`calculation-version:<source_calculation_id>:<random_uuid>`.

Один и тот же ключ сохраняется при сетевом повторе текущего черновика.

В Edge payload не входят:

- ID исходных строк;
- `calculation_id` и `lead_id` строк;
- суммы строк;
- прибыль и маржа;
- status и version number;
- ссылки на КП и заказ;
- actor ID;
- `created_by` и `updated_by`.

Сервер вычисляет эти значения самостоятельно.

## Безопасность данных

Редактор:

- работает только с расчётами текущей открытой заявки;
- проверяет совпадение `source.lead_id` с route lead ID;
- повторно проверяет source `updated_at` перед production INSERT;
- блокирует production legacy save при duplicate version inventory;
- не меняет исходный расчёт;
- не копирует технические ID строк в новую версию;
- не копирует ссылки на КП и заказ;
- не использует service-role key;
- не вызывает staging Edge Function из production;
- не выполняет direct RPC;
- не изменяет Auth, RLS, grants, policies или схему Supabase.

## Адаптивность

Редактор проверяется для:

- 360 px;
- 390 px;
- 768 px;
- 1366 px.

На мобильном экране каждая позиция отображается отдельной карточкой, а итоговые показатели располагаются одной колонкой.

## Ручная проверка production

1. Открыть заявку, в которой уже есть сохранённый расчёт.
2. Убедиться, что одновременно видны сохранённые версии и единый конструктор.
3. Нажать `Изменить / новая версия`.
4. Проверить, что все строки исходного расчёта появились в редакторе.
5. Проверить подпись `Рабочая CRM`.
6. Изменить количество или цену клиенту.
7. Проверить пересчёт суммы, прибыли и маржи.
8. Добавить и удалить ручную позицию.
9. Перед сохранением изменить source calculation в другой вкладке и убедиться, что preflight блокирует INSERT.
10. Для заявки с повторяющимся номером версии убедиться, что редактор не открывается.
11. Сохранить новую версию для чистой заявки.
12. Убедиться, что она появилась в той же заявке.
13. Убедиться, что старый расчёт, его КП и заказ не изменились.
14. Нажать `Новый пустой расчёт` и убедиться, что конструктор доступен без создания новой заявки.
15. Повторить проверку на ширине 390 px.

## Ручная проверка staging

Проверка возможна только после создания отдельного временного staging Auth user и synthetic fixtures:

1. открыть CRM со staging config;
2. войти staging-пользователем с ролью manager;
3. открыть synthetic source calculation;
4. проверить подпись `Тестовый staging`;
5. сохранить новую версию;
6. подтвердить HTTP 201 или безопасный HTTP 200 replay;
7. проверить отсутствие browser POST/PATCH/DELETE к таблицам;
8. проверить один вызов `leader-crm-calculations`;
9. проверить safe response и обновлённый список;
10. выполнить cleanup fixtures и Auth user.

На момент этапа staging содержит 0 Auth users, поэтому authenticated browser E2E не считается выполненным.

## Supabase boundary

В рамках этого этапа:

- production и staging DDL не выполняются;
- данные вручную не изменяются;
- Edge Functions не развёртываются;
- production server action не включается;
- production direct-write path не удаляется до отдельного rollout;
- `nav_*`, `parket_*` и `broker_*` не затрагиваются.
