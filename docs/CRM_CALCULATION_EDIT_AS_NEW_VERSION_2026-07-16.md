# Правки расчёта через новую версию

Дата: 16 июля 2026 года.

## Проблема интерфейса

В карточке существующей заявки два модуля использовали один DOM-контейнер `calculationsBox`:

- единый конструктор расчёта;
- список сохранённых версий.

Модуль сохранённых версий мог полностью заменить содержимое контейнера после того, как единый конструктор уже был отрисован. В результате сотрудник видел старые расчёты, но не видел форму нового расчёта и не мог продолжить работу в текущей заявке.

Эта интерфейсная ошибка исправлена: создание новой заявки для изменения стоимости, количества, материала или состава работ не требуется.

## Доступные действия

В существующей заявке сохраняются два разных сценария:

1. `Новый пустой расчёт` — открывает действующий единый конструктор для ещё одного самостоятельного расчёта в этой же заявке.
2. Создание новой версии сохранённого расчёта — отдельный сценарий, который допускается только через атомарный серверный action.

В production второе действие сейчас отображается как:

`Новая версия — недоступно`.

Кнопка имеет `aria-disabled=true` и объясняет, что безопасное сохранение появится только после отдельного production Edge/RPC rollout.

## Подготовка новой версии

В exact staging окружении действие `Изменить / новая версия`:

- копирует все позиции исходного расчёта;
- сохраняет категорию, тип, единицу, количество, себестоимость, цену клиенту, комментарий и структурированные характеристики;
- позволяет менять название, потребность и комментарий для клиента;
- позволяет менять количество, себестоимость и цену каждой строки;
- позволяет удалить строку;
- позволяет добавить ручную позицию;
- сразу пересчитывает суммы, прибыль и маржу;
- старая версия не обновляется и не удаляется;
- существующие КП и заказ продолжают ссылаться на старую версию;
- новая запись получает статус `Черновик`;
- новая запись не наследует `commercial_offer_id` и `order_id`.

## Номер и заголовок версии

Номер новой версии определяется сервером по правилу:

`max(version_number) + 1`.

Browser не передаёт `version_number`.

Staging Edge/RPC вычисляет номер внутри транзакции и advisory lock. Исторические дубли не перенумеровываются автоматически и блокируют создание до отдельного аудита.

Автоматический заголовок и пользовательский заголовок различаются. Для автоматического заголовка browser передаёт `title=null`, чтобы сервер сформировал правильный суффикс после фактического назначения номера. Пользовательское название передаётся явно и не перезаписывается.

Модель `calculationVersionLegacyPreflight` остаётся чистой тестируемой моделью проверки source timestamp и duplicate inventory. Она не выполняет запросов и больше не используется для production browser INSERT.

Подробный title-intent contract находится в `CRM_CALCULATION_VERSION_TITLE_INTENT_2026-07-16.md`.

## Исправление конфликта контейнеров

Добавлен browser compatibility layer:

- сохранённые версии перемещаются в отдельный `savedCalculationsWorkspace`;
- единый конструктор восстанавливается в `calculationsBox`;
- `MutationObserver` повторяет восстановление после обновления списка сохранённых расчётов;
- сохранённый список и конструктор больше не заменяют друг друга;
- старый дублирующий упрощённый список конструктора скрывается визуально;
- подробный список сохранённых версий остаётся основным.

## Маршрут сохранения

Редактор выбирает путь только по exact staging URL из `V4_CONFIG.supabaseUrl`.

### `staging_edge`

Используется только при URL проекта `otulfnouybahfnsycxqn`.

Редактор:

- проверяет canonical permission `calculations.write`;
- сохраняет стабильный idempotency key на время работы с черновиком;
- передаёт source calculation и его `updated_at`;
- вызывает `leader-crm-calculations` через текущую JWT-сессию;
- передаёт только разрешённую проекцию строк;
- после успеха перечитывает список расчётов;
- показывает подпись `Тестовый staging`.

В этом режиме browser INSERT/DELETE не выполняются. Расчёт, позиции и receipt создаются атомарно через Edge/RPC.

### `production_locked`

Используется для текущего production URL `ofewxuqfjhamgerwzull` и любого URL, который не является exact staging URL.

В этом режиме:

- действие версии блокируется до загрузки исходных строк;
- редактор не выполняет browser INSERT, UPDATE, DELETE или UPSERT;
- browser INSERT/DELETE удалены из `calculation-version-editor-v1.js`;
- compensating delete удалён;
- staging Edge Function не вызывается;
- production server action не включается;
- исходный расчёт и его связи не меняются;
- пользователь получает понятное сообщение о причине блокировки.

Обычный `Новый пустой расчёт` продолжает открывать существующий единый конструктор и этим этапом не изменяется.

## Idempotency и payload

Для staging создаётся ключ формата:

`calculation-version:<source_calculation_id>:<random_uuid>`.

Один и тот же ключ сохраняется при безопасном повторе текущего черновика.

В Edge payload не входят:

- ID исходных строк;
- `calculation_id` и `lead_id` строк;
- суммы строк;
- прибыль и маржа;
- status и version number;
- ссылки на КП и заказ;
- actor ID;
- `created_by` и `updated_by`.

Сервер вычисляет эти значения самостоятельно.

## Безопасность данных

Редактор:

- работает только с расчётами текущей открытой заявки;
- проверяет совпадение `source.lead_id` с route lead ID;
- не меняет исходный расчёт;
- не копирует технические ID строк в новую версию;
- не копирует ссылки на КП и заказ;
- не использует service-role key;
- не вызывает staging Edge Function из production;
- не выполняет direct RPC;
- не содержит прямых write-запросов к таблицам расчётов;
- не изменяет Auth, RLS, grants, policies или схему Supabase.

## Адаптивность

Интерфейс проверяется для:

- 360 px;
- 390 px;
- 768 px;
- 1366 px.

На мобильном экране заблокированное действие занимает полную ширину и не выглядит активным. В staging каждая редактируемая позиция отображается отдельной карточкой, а итоговые показатели располагаются одной колонкой.

## Ручная проверка production

1. Открыть заявку с сохранённым расчётом.
2. Убедиться, что одновременно видны сохранённые версии и единый конструктор.
3. Проверить текст кнопки `Новая версия — недоступно`.
4. Проверить `aria-disabled=true`.
5. Нажать кнопку и убедиться, что редактор и Network write не запускаются.
6. В Network подтвердить отсутствие POST, PATCH и DELETE к `leader_lead_calculations` и `leader_lead_calculation_items`.
7. Подтвердить отсутствие вызова `leader-crm-calculations` из production URL.
8. Нажать `Новый пустой расчёт` и убедиться, что единый конструктор доступен в этой же заявке.
9. Повторить проверку на ширине 390 px.

## Ручная проверка staging

Проверка возможна только после создания отдельного временного staging Auth user и synthetic fixtures:

1. открыть CRM с exact staging URL;
2. войти staging-пользователем с ролью manager;
3. открыть synthetic source calculation;
4. проверить подпись `Тестовый staging`;
5. проверить действие `Изменить / новая версия`;
6. сохранить новую версию;
7. подтвердить HTTP 201 или безопасный HTTP 200 replay;
8. проверить отсутствие browser POST/PATCH/DELETE к таблицам;
9. проверить один вызов `leader-crm-calculations`;
10. проверить safe response и обновлённый список;
11. выполнить cleanup fixtures и Auth user.

На момент этапа staging содержит 0 Auth users, поэтому authenticated browser E2E не считается выполненным.

## Supabase boundary

В рамках этого этапа:

- production и staging DDL не выполняются;
- production и staging данные не изменяются;
- Edge Functions не развёртываются;
- production server action не включается;
- production direct-write path удалён только из browser source;
- staging `leader-crm-calculations` остаётся без изменений;
- `nav_*`, `parket_*` и `broker_*` не затрагиваются.

Production rollout по-прежнему требует отдельного решения владельца, migration/RPC/index, Edge deployment и проверку перед изменением маршрута с `production_locked`.
