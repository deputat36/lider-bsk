# Правки расчёта через новую версию

Дата: 16 июля 2026 года.

## Проблема

В карточке существующей заявки два модуля использовали один DOM-контейнер `calculationsBox`:

- единый конструктор расчёта;
- список сохранённых версий.

Модуль сохранённых версий мог полностью заменить содержимое контейнера после того, как единый конструктор уже был отрисован. В результате сотрудник видел старые расчёты, но не видел форму нового расчёта и не мог внести правки без создания новой заявки.

Это интерфейсная ошибка. Новая заявка для изменения стоимости, количества, материала или состава работ не требуется.

## Исправленный сценарий

В каждой существующей заявке постоянно доступны два действия:

1. `Новый пустой расчёт` — открывает единый конструктор для ещё одного независимого расчёта в этой же заявке.
2. `Изменить / новая версия` — копирует выбранный сохранённый расчёт в отдельный редактируемый черновик.

При создании новой версии:

- копируются все позиции;
- сохраняются категория, тип, единица, количество, себестоимость, цена клиенту, комментарий и структурированные характеристики;
- можно менять название, потребность и комментарий для клиента;
- можно менять количество, себестоимость и цену каждой строки;
- можно удалить строку;
- можно добавить новую ручную позицию;
- суммы, прибыль и маржа пересчитываются сразу;
- старая версия не обновляется и не удаляется;
- существующие КП и заказ продолжают ссылаться на старую версию;
- новая запись получает статус `Черновик`;
- новая запись не наследует `commercial_offer_id` и `order_id`.

## Номер версии

Номер новой версии определяется не по количеству строк, а по правилу:

`max(version_number) + 1`.

Перед сохранением редактор повторно читает номера версий текущей заявки, чтобы не использовать устаревшее значение интерфейса.

Исторические дубли не перенумеровываются автоматически.

## Исправление конфликта контейнеров

Добавлен browser compatibility layer:

- сохранённые версии перемещаются в отдельный `savedCalculationsWorkspace`;
- единый конструктор восстанавливается в `calculationsBox`;
- `MutationObserver` повторяет восстановление после обновления списка сохранённых расчётов;
- сохранённый список и конструктор больше не заменяют друг друга;
- старый дублирующий упрощённый список конструктора скрывается визуально;
- подробный список сохранённых версий остаётся основным.

## Сохранение

Новая версия использует существующие production-таблицы:

- `leader_lead_calculations`;
- `leader_lead_calculation_items`.

Запись выполняется в два шага по действующему CRM-механизму:

1. создаётся расчёт;
2. создаются его позиции.

Если позиции не сохранились, созданный пустой расчёт удаляется compensating rollback-запросом.

Подготовленный серверный action `calculation.create_version` пока развёрнут только в staging и в production не используется. После отдельного production rollout browser-сценарий должен быть переключён на атомарную Edge/RPC-команду.

## Безопасность данных

Редактор:

- работает только с расчётами текущей открытой заявки;
- проверяет совпадение `source.lead_id` с route lead ID;
- не меняет исходный расчёт;
- не копирует технические ID строк в новую версию;
- не копирует ссылки на КП и заказ;
- не использует service-role key;
- не вызывает staging Edge Function из production;
- не изменяет Auth, RLS, grants, policies или схему Supabase.

## Адаптивность

Редактор проверяется для:

- 360 px;
- 390 px;
- 768 px;
- 1366 px.

На мобильном экране каждая позиция отображается отдельной карточкой, а итоговые показатели располагаются одной колонкой.

## Ручная проверка

1. Открыть заявку, в которой уже есть сохранённый расчёт.
2. Убедиться, что одновременно видны сохранённые версии и единый конструктор.
3. Нажать `Изменить / новая версия`.
4. Проверить, что все строки исходного расчёта появились в редакторе.
5. Изменить количество или цену клиенту.
6. Проверить пересчёт суммы, прибыли и маржи.
7. Добавить и удалить ручную позицию.
8. Сохранить новую версию.
9. Убедиться, что она появилась в той же заявке.
10. Убедиться, что старый расчёт, его КП и заказ не изменились.
11. Нажать `Новый пустой расчёт` и убедиться, что конструктор доступен без создания новой заявки.
12. Повторить проверку на ширине 390 px.

## Supabase boundary

В рамках этого этапа:

- production и staging DDL не выполняются;
- данные вручную не изменяются;
- Edge Functions не развёртываются;
- production server action не включается;
- `nav_*`, `parket_*` и `broker_*` не затрагиваются.
