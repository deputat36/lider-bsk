# План улучшения сайта и связки с CRM РА «Лидер»

Дата: 2026-07-10.

Основание: `docs/FULL_SITE_CRM_AUDIT_2026-07-10.md`.

Цель: сделать цепочку публичной заявки безопасной, доказуемой, наблюдаемой и удобной для ежедневной работы, не ломая production CRM.

## Принципы

1. Не менять `nav_*`, `nav-v2-*`, Parket и Broker контуры.
2. Не удалять данные, индексы, политики или функции без отдельной проверки.
3. Любое изменение public ingestion сначала проходит статические тесты и end-to-end проверку.
4. DDL выполняется только миграцией.
5. Edge Function deploy выполняется только после сверки source с GitHub и плана отката.
6. UI-скрытие не считается авторизацией: права должны подтверждаться сервером.
7. Исторические заявки без `request_id` не переписываются автоматически.

## Этап 0. Актуализация и CI-защита

Статус: выполняется в ветке `audit/site-crm-full-2026-07-10`.

Задачи:

- обновить CRM audit helper с v8 до v9;
- создать checklist v9;
- добавить единый контрактный тест цепочки;
- добавить ручной запуск workflow;
- зафиксировать полный аудит и план;
- вывести `request_id` в обычном списке и карточке заявки.

Критерии приёмки:

- статический тест подтверждает endpoint, request_id, honeypot, audit results и CRM trace;
- CRM не содержит пользовательской маркировки v8;
- новые файлы не содержат секретов;
- production Supabase не изменяется.

## Этап 1. Ручное доказательство end-to-end цепочки

Приоритет: P0.

Задачи:

1. Отправить новую тестовую заявку через `request.html`.
2. Сопоставить номер обращения на сайте с `leader_leads` и audit.
3. Проверить `Цепочка полная` в CRM.
4. Проверить повторный `request_id`.
5. Проверить honeypot.
6. Проверить отклонённый пустой запрос.
7. Сохранить результаты без публикации персональных данных.

Критерии приёмки:

- accepted создаёт ровно одну заявку и audit;
- duplicate не создаёт вторую заявку;
- suspicious и rejected не создают заявку;
- все ответы возвращают ожидаемый `request_id`;
- CRM открывает принятую заявку из trace;
- результаты записаны в отдельный тестовый отчёт.

## Этап 2. Закрытие прямого anon INSERT

Приоритет: P0.

Целевая архитектура:

`браузер → leader-public-lead → service role / приватный RPC → атомарная запись lead + audit`.

Задачи:

1. Подготовить новый source Edge Function в GitHub.
2. Выбрать один способ записи:
   - service role внутри Edge Function; либо
   - SECURITY DEFINER RPC в закрытой схеме с execute только для service role.
3. Создать транзакционный RPC для заявки и accepted audit.
4. Подготовить миграцию revoke прямого `anon INSERT`.
5. Добавить тесты CORS, duplicate, suspicious, rejected и audit failure.
6. Выполнить staging/preview проверку.
7. Развернуть функцию и миграцию с планом отката.

Критерии приёмки:

- прямой REST insert с anon key отклоняется;
- публичная форма продолжает работать;
- accepted создаётся атомарно с заявкой;
- audit negative scenarios сохраняются;
- service role не попадает в GitHub или браузер;
- Advisor не показывает новых проблем `leader_*`.

Риск: высокий. Production deploy только отдельным подтверждённым этапом.

## Этап 3. Серверная матрица ролей CRM

Приоритет: P0 до подключения новых сотрудников.

Задачи:

1. Сформировать action map для `leader-crm-leads` и `leader-crm-orders`.
2. Сопоставить действия ролям из `leader_role_permissions`.
3. Добавить серверную функцию `requireAction(profile, action)`.
4. Запретить designer/installer/contractor/accountant действия вне их зоны.
5. Проверить прямые browser table queries и RLS.
6. Согласовать RLS helper: заменить общий `leader_has_access()` там, где нужна роль.
7. Добавить негативные тесты каждой роли.

Минимальная модель:

- owner/admin — полный доступ;
- manager — заявки, клиенты, расчёты, КП и клиентская часть заказов;
- designer — только дизайн-задачи и необходимые связанные данные;
- production/contractor — только производственные задания;
- installer — только монтаж;
- accountant — оплаты, расходы и разрешённая часть заказов.

Критерии приёмки:

- запрет действует на сервере, даже если пользователь вручную вызывает API;
- UI и сервер используют одну версию role/action map;
- действующие owner/admin/manager сценарии не ломаются;
- тесты подтверждают 403 для запрещённых действий.

Приоритет: P1.

- показывать нормализованный телефон и source page path;

- добавить сводку разрывов цепочки;
- ввести контроль заявок без следующего контакта;
- подготовить безопасный отчёт по старым заявкам без `request_id`;
- улучшить дедупликацию клиентов по нормализованному телефону.

Критерии приёмки:

- менеджер находит заявку по номеру обращения без открытия аудита;
- `request_id` копируется одним действием;
- разрывы `lead_without_audit` и `audit_without_lead` видны владельцу/администратору;
- исторические данные не меняются автоматически.

## Этап 6. SEO, контент и производительность сайта

Приоритет: P1/P2.

Задачи:

1. Синхронизировать sitemap со всеми индексируемыми страницами.
2. Обновить cache markers главной страницы.
3. Ужесточить CI против старых версий CSS/JS.
4. Унифицировать JSON-LD:
   - Organization/LocalBusiness;
   - Service;
   - BreadcrumbList;
   - FAQPage.
5. Перевести упрощённые страницы на единый фирменный шаблон.
6. Постепенно вынести общий inline CSS.
7. Добавить реальные кейсы, сроки, материалы и требования к расчёту.
8. Провести внешний Lighthouse и мобильный browser audit.
9. Проверить юридический текст согласия и политики.

Критерии приёмки:

- каждая индексируемая страница имеет title, description, canonical и находится в sitemap;
- sitemap не содержит CRM/nav;
- мобильная версия не имеет горизонтального скролла;
- формы и CTA работают на всех посадочных;
- cache markers соответствуют актуальным файлам;
- нет регрессии Core Web Vitals после объединения стилей.

## Этап 7. Нормализация миграций и release process

Приоритет: P1 перед крупными изменениями БД.

Задачи:

- сопоставить live migration history и SQL snapshots GitHub;
- сформировать безопасную baseline migration;
- запретить случайный `supabase db push` из ненормализованной истории;
- добавить preview branch/staging процедуру;
- описать rollback Edge Function и migrations;
- добавить release checklist для сайт/CRM/Supabase.

Критерии приёмки:

- новая миграция воспроизводится на чистой branch database;
- production drift измерим;
- release не требует ручного исполнения неизвестных SQL-файлов;
- rollback документирован до deploy.

## Этап 8. Текущий автономный порядок

Без production-риска можно выполнять последовательно:

1. CI и документация.
2. Отображение request_id в CRM.
3. Sitemap и безопасные SEO-проверки.
4. Cache markers небольших файлов.
5. Единые шаблоны отдельных посадочных страниц.
6. Подготовка, но не применение, миграций и Edge Function hardening.

Требуют отдельного production-этапа:

- revoke anon INSERT;
- service-role/private RPC ingestion;
- изменение RLS;
- role/action enforcement;
- rate limit;
- backfill исторических данных;
- изменение Auth-настроек.

## Метрики результата

- 100% новых публичных заявок имеют `request_id`;
- 100% accepted-заявок имеют audit;
- 0 вторых заявок при duplicate request_id;
- 0 прямых anon REST inserts после hardening;
- 0 запрещённых серверных действий по роли;
- 100% индексируемых страниц отражены в sitemap;
- время поиска заявки по request_id — до 30 секунд;
- доля активных заявок без следующего контакта снижается до операционно согласованного уровня.
