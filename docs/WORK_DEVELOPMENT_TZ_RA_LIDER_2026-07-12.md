## 5. Режим работы с учётом ChatGPT Plus

Автономные запуски являются ограниченным ресурсом.

Официальная справка OpenAI для Agent mode указывает для Plus 40 начальных пользовательских запусков в месяц. Промежуточные уточнения и авторизация внутри уже начатого запуска не считаются отдельными, а scheduled tasks считаются. Фактический счётчик интерфейса считать источником истины, если условия тарифа изменятся.

Поэтому один запуск Work должен выполнять один крупный этап или 2–4 тесно связанные задачи.

Запрещено расходовать запуск на:

- повтор полного аудита без причины;
- один незначительный текстовый marker;
- один Issue-комментарий;
- повторение уже выполненной проверки;
- scheduled task без прямого запроса;
- перечитывание всех документов, когда есть continuation anchor.

Рекомендуемый бюджет одного запуска:

- 2–6 содержательных коммитов;
- 1–3 полезных комментария в Issues;
- одна законченная функция или один законченный слой защиты;
- один итоговый handoff.

Проекты ChatGPT на Plus поддерживают ограниченное число файлов. Не загружай репозиторий файлами в Project. GitHub должен оставаться источником кода, документации и тестов.

## 10. Уже реализовано — не делать повторно

### 10.1 Публичные формы

- retry idempotency;
- pending `request_id`;
- same-payload retry;
- duplicate handling;
- privacy-safe fingerprint.

Отдельно остаётся end-to-end browser proof публичной цепочки.

### 10.2 Авторизация

- profile-first boot;
- рабочие данные загружаются только после активного CRM-профиля;
- `crm-ready` не должен испускаться до проверки профиля.

### 10.3 UI-роли

Есть консервативная UI-матрица ролей и минимизация производственных данных.

Это defense-in-depth, а не завершённый server-side RBAC.

### 10.4 Статусы

Создан `status-transitions-v1.js`.

Registry используется в:

- операционном качестве лидов;
- UI заявок;
- КП;
- представлениях заказов;
- редакторе производства;
- редакторе монтажа;
- производственных алертах и сводке.

Не возвращать отдельные hardcoded terminal sets без обоснования.

Неизвестные raw-статусы должны оставаться видимыми и не переписываться автоматически.

### 10.5 Операционные очереди

Реализованы read-only очереди:

- лиды без ответственного;
- лиды без следующего контакта;
- просроченные контакты;
- потребности ниже 80%;
- заказы без расходов;
- заказы без ответственного;
- просроченные заказы;
- заказы, которым нужен дизайн, но нет design task;
- неизвестные статусы.

Очереди должны минимизировать данные и не выполнять записи.

### 10.6 Акты выполненных работ

Реализован source-only черновик:

- создание из карточки заказа;
- редактирование;
- A4 preview;
- печать/PDF через браузер;
- автоподстановка реквизитов при наличии настроек;
- отсутствие себестоимости и прибыли.

Постоянное хранение, юридическая нумерация, Storage и server action пока не развёрнуты.

### 10.7 Быстрый старт и обучение

Реальный quick-start:

- пять рабочих этапов;
- automatic evidence;
- completeness threshold 80%;
- успешный финал: order closed, production issued либо installation completed;
- cancellation не считается выполнением;
- состояние хранится только в localStorage.

Локальный тренажёр:

- `leader_crm_v4_training_scenario_v1`;
- отдельный от реального quick-start;
- вымышленный заказ баннера;
- пять последовательных шагов;
- никаких Supabase writes;
- Issue #230 содержит manual verification.

## 13. Правила разработки

Перед изменением большого файла:

1. получи его полностью;
2. проверь SHA;
3. убедись, что ответ не усечён;
4. используй точечный patch;
5. не восстанавливай неизвестные участки;
6. после изменения повторно прочитай файл.

Если безопасный patch невозможен:

- используй sidecar;
- создай pure model;
- добавь explicit import;
- подготовь patch artifact;
- не переписывай большой файл наугад.

Pure model должен:

- не обращаться к DOM;
- не создавать Supabase client;
- не выполнять network/write;
- тестироваться через Node assert.

UI sidecar должен:

- иметь idempotent boot guard;
- не дублироваться после событий;
- учитывать роль;
- минимизировать SELECT;
- иметь понятный partial mode;
- иметь manual Network test.

## 14. Приватность

Read-only панели и очереди должны получать минимальные поля.

Не запрашивать без необходимости:

- ФИО;
- телефон;
- email;
- сообщение;
- адрес;
- внутренние комментарии;
- полный JSON заказа;
- цены подрядчиков;
- себестоимость;
- прибыль;
- токены и секреты.

В localStorage не хранить реальные персональные данные, токены или рабочие payload.
