# CRM: плановые и подтверждённые фактические финансы

Дата: 2026-07-13.

## Цель этапа

Разделить в CRM три разных понятия:

1. плановые суммы заказа;
2. подтверждённые денежные движения;
3. фактическую прибыль, достоверность которой зависит от полноты внесённых расходов.

Главное правило: отсутствие строк в `leader_expenses` не означает нулевую фактическую себестоимость.

## Реализованный source-only контракт

Добавлены:

- `finance-plan-actual-model-v1.js` — чистая модель расчёта;
- `finance-plan-actual-panel-v1.js` — read-only сводка в разделе «Финансы»;
- обновлённая карточка заказа `order-card-v1.js`;
- behavior test;
- source checker;
- отдельный GitHub Actions workflow.

Модель не создаёт и не изменяет платежи, расходы или заказы.

## Термины

### План выручка

Значение `leader_orders.client_total`.

### План себестоимость

Значение `leader_orders.contractor_cost`.

### План прибыль

Значение `leader_orders.profit`. Если числовое значение отсутствует, модель использует разницу между плановой выручкой и плановой себестоимостью.

### Подтверждённые оплаты

Учитываются только строки `leader_payments`, где:

- `is_confirmed = true`;
- статус не является отменённым или аннулированным.

`Возврат`, `Расход` и другие исходящие типы уменьшают чистые поступления.

### Подтверждённые расходы

Учитываются строки `leader_expenses` со статусами, содержащими признаки:

- `Проведён`;
- `Оплачен`;
- `Подтверждён`;
- `Выплачен`;
- `Завершён`;
- `Исполнен`.

Черновые, ожидающие, неизвестные и отменённые расходы в факт не включаются.

### Денежный результат

Подтверждённые чистые поступления минус подтверждённые расходы.

Денежный результат не называется фактической прибылью, если у заказа есть плановая себестоимость, но нет ни одной подтверждённой строки расхода.

### Фактическая прибыль не рассчитана

Состояние используется, когда:

- плановая себестоимость больше нуля;
- подтверждённых расходов по заказу нет.

### Предварительный результат

Используется, если подтверждённые расходы есть, но заказ ещё не закрыт.

### Предварительная фактическая прибыль

Используется для закрытого заказа с подтверждёнными расходами. Значение всё равно помечается предварительным, поскольку в схеме нет отдельного признака «все расходы внесены».

## Проверка раздела «Финансы»

1. Выполнить `Ctrl + F5`.
2. Войти под активным `owner`, `admin` или `accountant`.
3. Открыть вкладку «Финансы».
4. Найти блок «План и подтверждённый факт».
5. Убедиться, что блок не показывается роли без доступа к `finance_control`.
6. Сверить плановые суммы с заказами.
7. Сверить подтверждённые оплаты с `leader_payments`.
8. Убедиться, что при отсутствии расходов показано:
   - `Подтв. расходы: 0 ₽`;
   - `Денежный результат: 61 400 ₽` для текущего baseline;
   - `Фактическая прибыль не рассчитана`;
   - предупреждение об отсутствии подтверждённых расходов.
9. Проверить показатели покрытия оплат и покрытия расходов.
10. Нажать «Обновить факт».
11. Убедиться, что панель не дублируется.
12. Нажать «Обновить финансы» в основном разделе.
13. Убедиться, что дополнительная панель сохранилась и обновилась.
14. Открыть заказ из строки сводки.

## Проверка карточки заказа

1. Открыть заказ, у которого есть плановая себестоимость и нет расходов.
2. Проверить, что верхние показатели подписаны как плановые:
   - `План клиенту`;
   - `План себестоимость`;
   - `План прибыль`.
3. В блоке «План и подтверждённый факт» проверить:
   - подтверждённые приходы;
   - возвраты и исходящие движения;
   - чистые поступления;
   - долг клиента;
   - подтверждённые расходы;
   - денежный результат;
   - статус достоверности фактической прибыли.
4. При отсутствии расходов значение фактической прибыли должно быть `Не рассчитана`.
5. Разница «План / факт» в этом состоянии должна быть `—`, а не отрицательной или положительной суммой.
6. Каждая оплата должна иметь подпись:
   - `Учтено в подтверждённом факте`;
   - либо причину, почему строка не учтена.
7. Каждый расход должен иметь аналогичную подпись.
8. Отменённые и черновые движения не должны попадать в подтверждённый факт.

## Контрольные сценарии

### Сценарий A: нет платежей и расходов

Ожидается:

- чистые поступления 0 ₽;
- подтверждённые расходы 0 ₽;
- денежный результат 0 ₽;
- фактическая прибыль не рассчитана при плановой себестоимости больше нуля.

### Сценарий B: есть подтверждённая оплата, расходов нет

Ожидается:

- оплата входит в чистые поступления;
- денежный результат отражает поступление;
- фактическая прибыль не рассчитывается.

### Сценарий C: есть неподтверждённая оплата

Ожидается:

- строка видна в карточке;
- строка помечена как неучтённая;
- сумма не увеличивает подтверждённые поступления.

### Сценарий D: есть возврат клиенту

Ожидается:

- подтверждённый возврат уменьшает чистые поступления;
- долг и денежный результат пересчитываются.

### Сценарий E: есть проведённый расход

Ожидается:

- расход уменьшает денежный результат;
- фактический результат становится предварительным;
- если заказ не закрыт, интерфейс предупреждает, что сумма будет меняться.

### Сценарий F: расход отменён или находится в черновике

Ожидается:

- расход не включается в подтверждённый факт;
- карточка показывает причину исключения.

### Сценарий G: платёж или расход не связан с активным заказом

Ожидается:

- сумма не добавляется к результату активных заказов;
- общая панель показывает отдельное предупреждение о движении без активного заказа.

## Network checklist

Открыть DevTools → Network и очистить журнал.

При открытии финансовой вкладки допустимы только read-only запросы:

- SELECT `leader_orders` с полями:
  `id,order_number,project_name,status,client_total,contractor_cost,profit,is_archived,created_at`;
- SELECT `leader_payments` с полями:
  `id,order_id,amount,payment_status,payment_type,is_confirmed,payment_date`;
- SELECT `leader_expenses` с полями:
  `id,order_id,amount,status,category,expense_date`.

Проверить отсутствие запросов:

- INSERT;
- UPDATE;
- DELETE;
- UPSERT;
- RPC;
- Edge Function write-команд.

Нажатие «Обновить факт» должно повторять только три read-only SELECT.

Открытие строки заказа использует существующие read-only запросы карточки. До явного использования штатных кнопок записи изменений быть не должно.

## Production boundary

В рамках этапа запрещено и не выполнялось:

- создание расходов;
- создание платежей;
- изменение заказов;
- backfill финансовых данных;
- Supabase DDL/DML;
- migrations;
- RLS и grants;
- Auth и Storage;
- Edge Function deploy;
- изменение `nav_*`, `nav-*`, `parket-*`, `broker-*`.

## Approval gates

Отдельное разрешение требуется для:

- добавления признака полноты расходов;
- автоматического создания расходов из плановой себестоимости;
- backfill исторических расходов;
- изменения статусов платежей и расходов;
- серверного financial-close gate;
- блокировки закрытия заказа без расходов;
- изменений схемы, RLS, grants или Edge Functions.
