# CRM staging lead workflow authenticated UI smoke v1

Дата: 24.07.2026

## Цель

Проверить реальную карточку заявки CRM v4 в браузере с авторизованным staging-пользователем и доказать, что рабочий маршрут заявки сохраняется через `leader-crm-leads-staging`, а не прямой записью из браузера.

Production-проект `ofewxuqfjhamgerwzull` не переключается и не изменяется.

## Обнаруженный разрыв

До runtime-проверки staging-таблица `public.leader_leads` содержала только шесть технических колонок. Карточка CRM v4 читает полный набор полей заявки, поэтому реальный UI не мог загрузиться, хотя изолированные транспортные тесты проходили.

Также на staging отсутствовал минимальный authenticated SELECT-контракт для профиля, заявки и истории заявки.

## Исправление staging

Применены и сохранены в репозитории staging-only миграции:

- `20260724_01_align_lead_card_read_contract.sql` — 33 совместимые колонки заявки и минимальные read-only RLS-политики для активного сотрудника;
- `20260724_02_lead_ui_smoke_cleanup_rpc.sql` — service-role-only очистка синтетической заявки, профиля и приватных квитанций команд.

Реальные данные из production не копировались.

## Runtime-сценарий

GitHub Actions создаёт через отдельный OIDC-bootstrap:

- временного подтверждённого Auth-пользователя с ролью `manager`;
- активный профиль;
- одну синтетическую заявку со статусом `Новая` и без ответственного.

Затем headless Chrome открывает настоящий `lead-card.js` и выполняет четыре действия:

1. «Взять в работу» — должно назначить текущего пользователя и перевести заявку в `В работе`.
2. `Ждём ответ` без будущего контакта — сервер обязан отклонить команду без события.
3. «Завтра 10:00» — будущий контакт должен сохраниться через Edge.
4. `Ждём ответ` — после будущего контакта статус должен сохраниться.

Ожидаемый результат:

- три успешные серверные команды;
- одна ожидаемо отклонённая команда;
- ровно три события истории;
- отсутствие дубликата события от старого browser-кода;
- серверное перечитывание итогового состояния;
- обязательная очистка Auth-пользователя, профиля, заявки и квитанций.

## Защита

Bootstrap принимает только GitHub OIDC-токен с точными условиями:

- repository: `deputat36/lider-bsk`;
- ref: `refs/heads/agent/staging-lead-workflow-ui-smoke-v1`;
- event: `push`;
- audience: `leader-staging-lead-workflow-ui-smoke`.

В исходном коде запрещён production project ref. После успешного прогона bootstrap должен быть заблокирован отдельной версией.

## Результат

Runtime-проверка запускается одноразовым trigger-файлом. Фактический результат и контроль нулевого остатка будут внесены после завершения GitHub Actions.
