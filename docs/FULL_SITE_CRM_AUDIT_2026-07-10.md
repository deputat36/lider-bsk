# Полный аудит сайта и связки с CRM РА «Лидер»

Дата: 2026-07-10.

Репозиторий: `deputat36/lider-bsk`.

Supabase project: `ofewxuqfjhamgerwzull`.

Контур:

`www.lider-bsk.ru → assets/public-lead-form.js → leader-public-lead v9 → leader_leads → leader_public_lead_audit → leader_request_trace → CRM v4`.

Аудит выполнен read-only для Supabase. Production DDL, DML, RLS, grants, Auth и Edge Functions не изменялись.

## Итог

Рабочая цепочка существует и технически связана правильно: публичная форма формирует `request_id`, передаёт источник и UTM, Edge Function нормализует данные, создаёт заявку, записывает audit-событие и возвращает номер обращения. CRM читает заявки и содержит виджет трассировки `request_id`.

Основные риски находятся не в отсутствии связки, а в её защите и доказанности:

1. У `anon` остаётся прямой `INSERT` в `leader_leads` и `leader_public_lead_audit`. Это позволяет обойти проверку origin, honeypot и формирование payload в Edge Function при наличии публичного ключа проекта.
2. `leader-crm-leads v12` проверяет JWT и активный профиль, но не ограничивает действия по роли. Активный дизайнер, монтажник или подрядчик потенциально может вызвать больше CRM-действий, чем показывает интерфейс.
3. В production подтверждена только одна полная трассировка текущего контракта. Сценарии `duplicate`, `suspicious`, `rejected` и `error` ещё не доказаны ручным end-to-end тестом.
4. Запись заявки и запись audit-события выполняются отдельными REST-запросами. При сбое аудита возможен статус `lead_without_audit`.
5. Публичный sitemap не содержит часть новых посадочных страниц.
6. Главная страница использует устаревшие cache markers формы и вспомогательного JS.

## Сильные стороны

### Публичная форма

- endpoint жёстко закреплён за `leader-public-lead`;
- `request_id` создаётся до отправки и возвращается пользователю;
- повторный клик блокируется;
- ответ Edge Function определяет фактический `request_id`;
- передаются page URL/path/title, `submitted_at`, UTM и user agent;
- honeypot передаётся на сервер и не отбрасывается только в браузере;
- пользователь видит понятный номер обращения;
- Яндекс Метрика получает результат и признак дубля.

### Edge Function

- разрешены только основные домены РА «Лидер»;
- есть ограничение размера тела запроса;
- текстовые поля ограничиваются по длине;
- телефон нормализуется;
- поддерживаются результаты `accepted`, `duplicate`, `suspicious`, `rejected`, `error`;
- дубли `request_id` не создают вторую заявку;
- секретный ключ не находится в публичном JavaScript.

### База и трассировка

- `request_id` защищён уникальным ограничением;
- `leader_leads` и `leader_public_lead_audit` используют RLS;
- `leader_request_trace` доступна только `authenticated` и работает как `security_invoker`;
- публичные роли не имеют чтения заявок и аудита;
- служебные `leader_*` SECURITY DEFINER функции не исполняются напрямую ролью `authenticated`.

### CRM

- заявки с сайта определяются по источнику и URL;
- есть фильтр заявок с сайта;
- audit показывает результат и причину;
- трассировка показывает `complete`, `lead_without_audit`, `audit_without_lead`, `missing`;
- из результата можно открыть карточку заявки;
- основной CRM-контур использует отдельный auth storage key.

## Проблемы по приоритету

### P0 — доказать рабочую цепочку

Production содержит только одну полную актуальную трассировку. Необходимо вручную доказать:

- новую принятую заявку;
- повтор того же `request_id`;
- honeypot;
- отклонённый пустой запрос;
- открытие заявки из CRM trace.

Без этого кодовый контракт проверен, но полный browser/runtime сценарий доказан недостаточно.

### P0 — прямой публичный INSERT обходит Edge Function

Сейчас `anon` имеет `INSERT` в:

- `leader_leads`;
- `leader_public_lead_audit`.

Edge Function тоже использует anon key. Поэтому любой клиент с публичным ключом может обратиться к REST API напрямую и обойти:

- allowlist origin;
- honeypot-логику;
- единый формат payload;
- нормализацию телефона;
- обязательную запись audit-события.

Целевая архитектура:

- запись разрешена только Edge Function через service role либо через узкий приватный RPC;
- прямой `anon INSERT` отозван миграцией;
- браузер знает только URL Edge Function и не получает служебные права.

Изменение нельзя применять без staging/end-to-end проверки, потому что оно затрагивает работающую публичную форму.

### P0 — серверная авторизация CRM не соответствует UI-ролям

`leader-crm-leads v12` проверяет:

- валидный JWT;
- наличие активного `leader_user_profiles`.

После этого активному пользователю доступны все маршрутизируемые действия функции. Проверки `owner/admin/manager/designer/installer/...` по конкретному действию нет.

RLS helper `leader_private.leader_has_access()` также проверяет только наличие активного профиля. UI скрывает вкладки по `leader_role_permissions`, но UI-скрытие не является серверной защитой.

Риск станет высоким сразу после добавления дизайнеров, монтажников, подрядчиков или бухгалтеров.

### P1 — audit не атомарен с созданием заявки

Сначала создаётся запись в `leader_leads`, затем отдельным запросом — `accepted` в audit. При сетевом или RLS-сбое второй операции заявка останется без audit.

Целевая архитектура: один серверный RPC/транзакция, создающий заявку и audit-событие атомарно.

### P1 — нет полноценного rate limit

Origin allowlist защищает браузерный CORS-сценарий, но не является защитой от серверных запросов без `Origin`. Ограничение размера тела полезно, но не ограничивает частоту запросов.

Нужно добавить мягкий rate limit с минимизацией персональных данных: hash IP/телефона, короткое окно, отдельный audit reason и понятный ответ клиенту.

### P1 — request_id недостаточно виден в обычной работе CRM

Сейчас `request_id` хорошо виден в разделе аудита, но не выводится в основном списке и карточке заявки. Менеджеру сложнее быстро сопоставить обращение клиента с записью CRM.

### P1 — неполный sitemap

В основном sitemap отсутствует часть новых публичных страниц, включая каталог и новые разделы полиграфии. Это снижает управляемость индексации и создаёт расхождение между сайтом и SEO-картой.

### P2 — cache markers главной

`index.html` использует:

- `assets/public-lead-form.css?v=3`;
- `assets/public-lead-form.js?v=4`;
- `assets/packages-link.js?v=1`.

После изменений пользователи могут дольше видеть старый CSS/JS. Нужна аккуратная синхронизация версий и последующее ужесточение CI.

### P2 — неоднородные страницы и inline CSS

Часть страниц выполнена в едином чёрно-оранжевом стиле, часть — в упрощённой системе. Большие inline-стили усложняют поддержку и кеширование.

### P2 — служебные страницы в корне

В корне репозитория остаются страницы другого контура. `deals-v2.html` имеет `noindex`, а `deal-card-v2.html` не содержит meta robots. Этот файл относится к Navigator и в рамках РА «Лидер» не изменялся, но риск случайной индексации нужно устранить в владельце соответствующего контура.
