# CRM v4: статусы строк платежей в подтверждённом факте — 2026-07-15

Связано: #217, #200.

## Цель

Использовать canonical домен `payment_record` при расчёте подтверждённых поступлений и возвратов.

`is_confirmed=true` остаётся обязательным, но сам по себе больше не считается достаточным. В подтверждённый факт включается только строка со статусом `Проведён` или его canonical alias `Проведен`.

## Правила

- `Планируется` → `planned` → не включается в факт;
- `Проведён` / `Проведен` → `posted` → может включаться при `is_confirmed=true`;
- `Отменён` / `Отменен` → `cancelled` → не включается;
- пустой или неизвестный статус → не включается;
- неподтверждённая строка → не включается независимо от статуса;
- направление прихода/возврата продолжает определяться существующим `payment_type`.

## Причины исключения

`confirmedPaymentEffect()` возвращает одну из причин:

- `empty_amount`;
- `not_confirmed`;
- `not_posted`;
- `cancelled`;
- `unknown_status`;
- `confirmed`.

Для каждого эффекта дополнительно доступны `statusKnown` и `statusKey`.

## Финансовая сводка

На уровне заказа и портфеля добавлены read-only показатели:

- `unknownPaymentStatusRows`;
- `notPostedPaymentRows`.

Предупреждения отдельно сообщают:

- количество платежей с неизвестным статусом;
- количество плановых платежей, ещё не включённых в факт;
- общее количество проигнорированных строк.

Это защищает фактические поступления и денежный результат от завышения непроведёнными или нераспознанными строками.

## Границы

Пакет не меняет:

- `leader_payments`;
- `leader_orders`;
- суммы, статусы и `is_confirmed` в production;
- существующий read-only SELECT панели;
- направление платежей;
- расходы и их текущую отдельную классификацию;
- Supabase schema, RLS, grants, policies, Auth или Edge Functions.

Новые INSERT, UPDATE, DELETE, UPSERT и RPC не добавляются.

## Автоматическая проверка

- `tools/test_crm_payment_record_status.mjs` проверяет canonical модель;
- `tools/test_finance_plan_actual.mjs` проверяет включение только posted+confirmed;
- `tools/check_crm_payment_record_status_registry.py` проверяет интеграцию и read-only границы;
- workflow `CRM finance plan actual check` и общий registry workflow выполняют проверки.

## Ручная проверка

На synthetic fixture в development/browser test:

1. создать четыре локальных строки представления: `Планируется`, `Проведён`, `Отменён`, неизвестный статус;
2. всем установить `is_confirmed=true`;
3. убедиться, что в факт входит только `Проведён`;
4. для `Проведён` с `is_confirmed=false` убедиться, что строка исключена как `not_confirmed`;
5. проверить предупреждения unknown/planned;
6. убедиться, что расчёт возврата остаётся отрицательным;
7. в Network убедиться, что открытие панели не создаёт POST, PATCH, INSERT, UPDATE, DELETE или RPC;
8. подтвердить отсутствие изменений production rows.

Server-side переходы платежей остаются approval-gated в #202/#204.
